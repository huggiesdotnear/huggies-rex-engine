- 🧬 one function per a file, clean clear sanke_case nameing for functions. and file name should match function name.
- 🧬 `========================================` comments at the top of the file between import statemnets, and at the bottom of the file. and in vaires places in the html files. never remove these comments.
- 🧬 please no camel case only snake_case or SCREAMING_SNAKE.
- frontend/lib/ts/ holds plain ts only. a file that renders jsx is a component and lives in frontend/lib/components/ (`balance_row.tsx`, `token_holder_row.tsx`), never in frontend/lib/ts/.
- frontend/lib/ts/ is split into a folder per page, and the folders mirror the components: `lib/ts/<page>/` holds the ts that page owns, `lib/ts/contract/<page>/` for a page under `app/contract/`, `lib/ts/token/<page>/` for a page under `app/token/`, and `lib/ts/shared/` for the ts more than one page uses. a page's own folder holds its loader, its store and its helpers.
- a file in `lib/ts/shared/` is used by MORE THAN ONE page. a file one page uses belongs in that page's folder, even if its name reads like a shared thing. a page folder must never hold a file another page needs — that is what `shared/` is for.
- the import files sit at the ROOT of frontend/lib/ts/, named after the css they mirror: `import-<page>.ts` next to `import-<page>.css`, `import-token.ts` next to `import-token.css`, and `import-app-wide.ts` for the app-wide components every page carries. a page with nothing of its own has no css file and no css import file — it links the base only. an import file is the page's ONE ENTRY — it holds ONLY imports, no logic, no functions, and the only exception is the app-wide and root files, which register the service worker — and the order of its imports is the page's order of life: the network pin first, then the page's own start or route script, then the page's components. a page's html loads its own import file and no other.
- a page's html loads ONE thing: the page's own import file. everything the page needs comes through it — the network pin (`hello.ts`), the page's own script (the route or the start script), and the page's components — and the order of the imports inside that file is what puts them in the right order.
- a ts file that belongs to ONE page is named `<prefix>_<pagename>_<what>.ts` — the prefix says which page owns it. `app_page_<pagename>_<what>.ts` for a page at the top of `app/` (e.g. `app_page_account_balances.ts`, `app_page_discover_token_search.ts`), `contract_page_<what>.ts` for a page under `app/contract/` (e.g. `contract_page_pumpopoly.ts`), `token_page_<what>.ts` for a page under `app/token/` (e.g. `token_page_token_types.ts`), `root_page_<what>.ts` for the splash page at `frontend/index.html` (e.g. `root_page_start.ts`). a ts file used by more than one page keeps a plain name (`token_info.ts`, `token_link.ts`).
- a tsx component file follows the SAME prefix as its ts siblings: `app_page_account_id_h1.tsx` for the account page, `contract_page_pumpopoly_player_stats.tsx` for the pumpopoly page. a tsx used by MORE THAN ONE page lives in `frontend/lib/components/shared/` and keeps a plain name (`id_jump_box.tsx`, `balance_row.tsx`, `balance_table.tsx`, `sort_keys_control.tsx`, `token_meta_grid.tsx`). a tsx used by ONE page lives in that page's own folder, `frontend/lib/components/<page>/`, mirroring the ts folders — `frontend/lib/components/contract/<page>/` for a page under `app/contract/`, `frontend/lib/components/token/<page>/` for a page under `app/token/`. a one-page component with NO mount id — a piece of another component — keeps a plain name (`error_card.tsx`, `stat_tile.tsx`, `switch_direction.tsx`, `code_block.tsx`). the components EVERY page carries live in `frontend/lib/components/app-wide/` (the loading bar, the nav, the auth button) — they belong to no one page. the mount id does NOT have to match the file name — it keeps the shorter form (`HUGGIES_COMPONENT_ACCOUNT_ID_H1`).
- a file's name says what it HOLDS, and two files whose names are one letter apart must not do different jobs. `app_page_discover_token_sort_options.ts` holds the options and `app_page_discover_token_sort_apply.ts` applies them; `token_icon_url.ts` builds the url and `token_icon_fetch.ts` fetches it; `token_amount_format.ts` formats and `token_amount_row.ts` composes the row. when two names nearly collide, the second one gets a word that says its job.
- a name must not say the OPPOSITE of what the file is. a list that is MARKED and not pinned is `app_page_discover_marked_tokens.ts`, not `pinned_tokens.ts`.
- a file's name must not promise a page it does not belong to. when a page has more than one loader, each is named for its own part (`app_page_account_balances.ts`, `app_page_account_transactions.ts`, `app_page_account_tx_details.ts`).
- css lives in `frontend/lib/css/`. `import.css` is the app-wide base and every page links it. the app-wide rules live in `frontend/lib/css/base/`, and a component's own rules live in `frontend/lib/css/components/HUGGIES_COMPONENT_<name>.css` — one css file per component, named after the mount id, and a component that needs no css gets no css file. that css file lives in a folder mirroring the component's own folder: `frontend/lib/css/components/<page>/` for a page's components, `frontend/lib/css/components/contract/<page>/` for a page under `app/contract/`, `frontend/lib/css/components/token/<page>/` for a page under `app/token/`, and `frontend/lib/css/components/shared/` for a shared component. the css folders mirror the component folders exactly. a rule lives with the component that owns it, so two files never style the same classes.
- a shared component's css lives in `frontend/lib/css/components/shared/<name>.css`, named after its tsx file, so the tsx and its css match one to one. a component with NO mount id — a shared one, or a page component that is a piece of another component — has its css named after its tsx file, in the folder that mirrors its own.
- a component's css file `@import`s the shared css it uses: `@import url(./shared/balance_table.css);`. the shared css then arrives with the component that needs it, and a page's `import-<page>.css` lists only the page's own components.
- css is scoped by the mount id. a page component's rules are written `#HUGGIES_COMPONENT_<name> <selector>`, so a rule reaches only the markup inside that component's own mount. a shared component has no mount id — it carries one class on its root (`.balance-table`) and its rules nest under that class.
- an element's BASE rules live in `frontend/lib/css/base/<element>.css` — one file per element (`a.css`, `code.css`), holding what EVERY instance of that element shares. a component that wants an element to look different writes its own rule under its mount id, and the id selector beats the base, so the override wins. never repeat a base rule in a component css.
- `base/code.css` owns the code chip: monospace, the text color, small, and breaking long ids. a code chip is NEVER dimmed with `opacity` — opacity blends the chip with whatever sits behind it, so on the red background it turns muddy. the font and the size tell the chip apart, not a faded color.
- `base/a.css` owns the link: the page text color and no underline. the bottom nav is a `nav a` rule, so it keeps its own look.
- a class is used ONLY where an element selector cannot say it: when the same element type appears twice with different rules (a card's label span and its value span), when it carries a state (`.is-active`, `.is-revealed`), or when it is a variant (`.is-dev`, `.is-dex`). everything else is a bare element selector — `p`, `a`, `code`, `strong`, `td`, `h2`.
- a page links the base and then `frontend/lib/css/import-<page>.css`, which holds only import statements. a page with nothing of its own gets no import file and links the base only.
- page content sits directly inside `<main>`. no wrapper div, no classes on the page's own markup — the page's html holds only the mount ids, and `main` is the column.
- every page has ONE loader FOLDER: `lib/ts/<page>/`, whose files do all of that page's fetching — a page that fetches one thing has a single `<prefix>_<pagename>.ts` (`app_page_burn.ts`), a page that fetches several has one file per thing (`app_page_account_balances.ts`, `app_page_account_transactions.ts`, `app_page_account_tx_details.ts`). the components read the loaded data and fetch nothing themselves, so the page's request list is knowable by reading its folder. see [PAGES/PATTERN.md](./PAGES/PATTERN.md) for the whole shape — the store, the start script and the one hook.
