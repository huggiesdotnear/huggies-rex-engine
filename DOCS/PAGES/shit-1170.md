# $SHIT

dedicated token page for `shit-1170.meme-cooking.near` -
`frontend/app/tokens/shit-1170.html`

a special page for one token. unlike the generic token page, this one
lists **every** holder from INTEAR's all-holders api and tags each of
them with a known-holder type. it is reached at
`/app/tokens/shit-1170.html`.

## LAYOUT

the page is laid out like the original SHIT holder app, with the
metadata moved to the bottom:

1. the **h1** — the contract account id, `shit-1170.meme-cooking.near`.
2. **HOLDERS BY GROUP** — the stacked bar and the per-group list.
3. **HOLDERS (n)** — the holder count, the tabs, and the holder table.
4. **TOKEN METADATA** — the metadata grid, at the bottom of the page.

the metadata grid reuses the regular token page's own look
(`huggies-token-meta` / `huggies-token-meta-row`), so the two pages
read the same and the metadata cannot drift away from it.

> --- WHY --- the metadata used to sit at the top of the page, above
> the holder list. the holder list is what this page is *for* — the
> tabs, the group breakdown, and the rows — and the metadata was
> pushing it below the fold. the metadata is still on the page, just
> at the bottom, where a reader who wants it scrolls down to it.

> --- WHY --- the metadata block shows neither the token description
> nor a link to the regular token page. the description is the token's
> own marketing copy and the regular token page already shows it, so
> on this page it was noise — and the link was a way out of a page
> the reader did not ask to leave. the summary fetch drops those
> fields too, so the api answer is smaller for them.

## METADATA

the metadata block sits at the **bottom** of the page and shows the
token summary: price, holder count, total supply, decimals, reputation,
liquidity, market cap, and the LP / pool reference. it is laid out in
the regular token page's own metadata grid, so the two pages read the
same.

- **total supply** is `1,000,000,000` SHIT with 18 decimals.
- **price** comes from the intear price api
  (`https://prices.intear.tech/price?token_id=...`), which answers a raw
  number as a plain string. when that call fails, the page falls back to
  INTEAR's `price_usd` from `GET /tokens`.
- **LP / pool reference** is the ref finance pool the token is priced
  against (`REF-5767`). the page reads the pool through the
  `get_pool` view on `v2.ref-finance.near` and derives the pool's
  implied price from the reserves and the paired token's price
  (`wrap.near`). the implied price and the pool TVL are shown next to
  the api price so the two can be compared. when the pool view fails the
  page still renders the summary and says why the LP reference is
  missing.

## HOLDERS

holders come from **INTEAR**, not FastNear. the page calls
`GET /holders` through the middleman (`api_intear_holders_get`) with
cursor pagination and a page size of 100, so the list is the full
holder set rather than a top-100 slice. the response's `total` is
shown next to the filter buttons, and a **LOAD MORE** button appears
while the response still carries a next cursor.

each holder row shows:

| column      | source                                                        |
| ----------- | ------------------------------------------------------------- |
| rank        | position in the loaded list                                   |
| account     | the account id, linked to the account page                    |
| amount      | the raw balance scaled by 18 decimals, with a K/M/B suffix    |
| usd         | the amount times the token price                              |
| % of supply | the balance as a share of the 1,000,000,000 SHIT total supply |
| type        | the known-holder tag                                          |

### % OF SUPPLY

the share of the total supply is computed on `BigInt` — the raw balance
and the raw supply are both 18-decimal integers — and only then scaled
to a percent, so the dust rows below 0.001% still rank correctly. the
display matches the original SHIT info page: two decimals above 0.01%,
three decimals above 0.001%, and `<0.001%` below that.

## TYPE TAGS

every holder is tagged with a known-holder type. the canonical map is
`KNOWN_HOLDERS_ACCOUNTS` from `@huggies/shit-bin`
(`src/const/mainnet/HOLDERS.ts`). that package is not a dependency of
this repo, so the map is kept as a **local copy** in
`frontend/lib/ts/shit_known_holders.ts` — keep it exactly in sync with
the source above.

the types are `dev`, `dex`, `vault`, `nft`, and `burn`. an account that
is not in the map is a `regular` holder.

| type    | icon |
| ------- | ---- |
| `dev`   | 👨‍💻   |
| `dex`   | 🔄   |
| `nft`   | 🖼️   |
| `vault` | 🏦   |
| `burn`  | 🔥   |
| regular | 👤   |

## TABS

the holder types are **tabs** — the same emoji buttons the original
SHIT holder app has, and the same set: `ALL` (💩), `DEV` (👨‍💻), `DEX`
(🔄), `NFT` (🖼️), `VAULT` (🏦), `BURN` (🔥), and `HOLDERS` (👤).

the tabs are **emoji only, on one row**. each tab shares the page
column equally between them, so they are all the same width no matter
which emoji is on them, and the row never wraps.

> --- WHY --- the tabs used to carry the type name and the group's
> percentage under the emoji. that is a lot of text for a small
> button: seven tabs of icon + label + percentage could not fit on one
> row without the labels shrinking or the row spilling out of the
> column. the percentage of each group lives in the HOLDERS BY GROUP
> list instead, where there is room for it.

> --- WHY --- the tabs used to be a flex row of auto-width pills. the
> widths came out different for every tab — `HOLDERS` is wider than
> `ALL` — so the row changed shape as the reader moved along it.

each tab carries its type name as an `aria-label` and a tooltip, so
the emoji still has a name for a screen reader and on hover.

filtering happens client-side over the pages already loaded — it does
not refetch.

## HOLDERS BY GROUP

under the heading, the page breaks the holder list down by group. each
group is a **white card**, the same card the old SHIT info page used
for its holder rows: a coloured stripe down the left edge for the type,
the icon and the name on the left, the holder count and the percentage
on the right.

each group shows:

- its icon and name
- how many holders it is made of
- **the share of the total supply it holds**

**the card of the active tab is the one picked out** — it gets a teal
outline. the tabs and the group list show the same thing from two
sides, so the reader can see at a glance which filter the holder list
under them is filtered by.

> --- WHY --- the section used to sit above a stacked bar — one slice
> per group, sized by its share. the bar said the same thing as the
> list under it, in a shape that took a whole extra row to say it, and
> the slices had to be read against each other to get anything out of
> them. the list says it outright, one number per group.

> --- WHY --- the group shares are computed on `BigInt`, the same way
> the per-row `% OF SUPPLY` is. the raw balances and the raw total
> supply are both 18-decimal integers, so the ratio is done on BigInt
> and only then scaled to a percent — floating point loses the groups
> that sit below 0.001%.

the shares are a share of the **total supply**, not a share of the
loaded holders. a group can therefore show more than the sum of the
percentages of the rows under it when the list is not fully loaded.

## LINK FROM THE TOKEN PAGE

the generic token page for this token links here with a quiet **💩 $SHIT**
easter-egg link under the auth button — the same treatment as the emoji
game link on the discover page. it only appears on this token's own
page, so the holder list is one click away from the regular token view
without shouting about it.
